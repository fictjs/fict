# Release Policy

This policy defines how Fict releases are prepared, verified, and documented.
It exists to keep package changelogs and stability promises aligned with the
engineering quality of the compiler/runtime.

## Versioning

Fict is currently `0.x` alpha. Until `1.0.0`, minor releases may include
breaking changes, but every breaking change must be called out in the package
changelog and release notes.

Starting with `1.0.0`, Fict follows SemVer:

- Patch: bug fixes, docs, diagnostics wording, non-breaking internal changes.
- Minor: new APIs, new compiler diagnostics, opt-in runtime capabilities.
- Major: public API breaks, compiler output ABI breaks, or changed default
  semantics for stable APIs.

Preview APIs such as `renderToPartial` are not frozen. They must stay marked as
Preview/experimental in docs and changelogs until the API freeze document moves
them to a stable tier.

## Changesets

Every user-visible package change must include a Changeset. The Changeset entry
must explain what changed in user terms, not just the package that changed.

Good:

```md
Fix tracked branch remounts so foreign input state is preserved when a fallback
branch is replaced.
```

Bad:

```md
fix
fix fict
update
```

Dependency-only releases may say that no API behavior changed, but they must
name the release train or compatibility reason:

```md
Publish the testing library with runtime and SSR 0.20 compatibility; no testing
API behavior changed.
```

## Changelog Quality Gate

Before publishing:

1. Run `pnpm version` to materialize package changelogs.
2. Review every changed `packages/*/CHANGELOG.md`.
3. Reject placeholder entries such as `fix`, `update`, `fix fict`, or package
   names without behavior.
4. Keep dependency update blocks generated by Changesets, but add a real
   release note when the package has a user-facing reason to publish.
5. Call out breaking changes under a `### Breaking Changes` heading.
6. Call out Preview/experimental changes explicitly.

The release PR should include the verification command output or CI link for:

- `pnpm release:verify`
- `pnpm release:compiler:verify` when compiler output, diagnostics, metadata,
  or optimizer behavior changed
- `pnpm size` when runtime or public entrypoints changed

## API Stability Labels

Use the stability tiers from `docs/api-freeze-v1.md`:

- Tier 1 public APIs require backward compatibility after v1.
- Tier 2 compiler ABI can change implementation details but must remain
  compatible with supported compiler output.
- Tier 3 advanced APIs should remain stable when practical.
- Tier 4 preview/experimental APIs can change, but docs must say so.

## Release Note Checklist

Each release note should answer:

- What user-visible behavior changed?
- Which package owns the behavior?
- Is this a bug fix, new capability, compatibility publish, or preview change?
- Does this affect strictGuarantee, compiler output, runtime scheduling,
  hydration/resume, or package metadata?
- Does the migration guide or API reference need an update?

If the answer is "no user-visible behavior changed," say that explicitly and
name the compatibility reason for the package publish.
